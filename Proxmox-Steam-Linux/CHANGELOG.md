# Changelog

All notable changes to `Proxmox-Steam-Linux/` are documented here. Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- **`README.md` "Known limitations / next steps" reframed: the two-phase design's actual goal — a real game, on a real server, verified with real players over the internet — is met, not just aspirational.** Valheim (`valheim-1`) ran a live session with 5 concurrent real players connecting from the internet; the server performed well. This is the real proof of the design, not the earlier systemd/`ss`/journal checks alone — those confirm the process is up and listening, not that it holds up under real gameplay. Also documents that this project was always meant as an interim/testing solution ahead of a more formal fleet-management layer for "Steam Engines" (Linux and, eventually, Windows) — not an end state in itself.

### Removed

- `PLANNING-INITIAL.md` — the design-conversation snapshot committed early on, before most of this project's actual implementation/debugging work happened. Logged here solely because the file existed in a prior commit, not because of any content judgment: everything in it is now either stated directly in `README.md` (design opinions, ingress model, the Phase A/B framing), superseded by the actual code and its own inline comments (role task sequences, file trees, variable listings), or stale relative to the real verification checklist below — checked section by section before removal, nothing unique was left behind.

### Added

- Initial project: Ansible-based SteamCMD dedicated-game-server deployment on a Proxmox VM, split into two playbooks with different jobs and lifecycles (see `README.md` "Two playbooks"):
  - `create-steam_linux.yaml` — provisions the base host: clones `T-Debian-13-Cloud`, applies cloud-init/sizing (resizing **both** VM disks, not just root — this host is meant to grow multiple future game-server installs), installs SteamCMD and 32-bit runtime dependencies. Non-Proxmox-API-independent, unlike playbook two. Roles: `proxmox_preflight`, `create_steam_vm`, `steam_prereqs`, `steamcmd_install`, `steam_base_verify`.
  - `create-steam_gameserver.yaml` — installs/updates **one** game-server instance (any Steam AppID) onto an already-provisioned host, entirely over SSH with no Proxmox API calls at all — data-driven via an instance vars file passed with `-e @<path>`. Roles: `steam_gameserver_instance` (generic — deliberately contains no game-specific knowledge, so it's the reuse point for future games and a possible future orchestration layer), `hlds_dm_config` (HLDS-specific `server.cfg`/`mapcycle.txt` rendering), `steam_gameserver_verify`.
  - `create-steam_linux_backup.yaml` — standalone on-demand VM backup playbook (`steam_backup` role), backs up the whole VM (base host + every instance) at once.
- `create_steam_vm` persists each VM it creates into this project's own static inventory (`inventory/host_vars/<hostname>.yaml` + `inventory/hosts.ini`), since `create-steam_gameserver.yaml` runs as a separate `ansible-playbook` invocation later with no access to the VM-creation run's cached facts.
- Phase A validation instance: `hlds-dm01` (HLDS / Steam AppID 90, anonymous login) running the 7 stock deathmatch maps (crossfire, datacore, stalkyard, snark_pit, boot_camp, subtransit, undertow) on a 10-minute `mp_timelimit` rotation — committed directly as `gameservers/hlds-dm01.vars.yaml` (not gitignored/`.example`, since it carries no secrets or site-specific values), verified via systemd `is-active` plus a UDP-port-bound check (`ansible.builtin.wait_for` doesn't support UDP).
- `.example` config files (`hosts.ini.example`, `group_vars/{proxmox_pve1,steam_linux}/vars.yaml.example`); real files gitignored — this repo is public. No project-local `vault.yaml`/`.example` yet: Phase A's anonymous SteamCMD login needs no secret (see `README.md` "Known limitations" for when that changes).
- `Deploy.sh` / `Install-Prerequisites.sh` convenience scripts, adapted from `Proxmox-Forgejo`'s (dropped the project-local-vault check, since none exists yet).
- README.md documents Phase B's design intent (data-driven `steam_gameservers` list, `<game>_config` roles per new game, a possible future Pterodactyl-like orchestration layer targeting Proxmox VMs or Kubernetes pods) as "Known limitations / next steps" — not built yet.
- Second worked instance definition: `gameservers/valheim-1.vars.yaml` (Valheim dedicated server, AppID 896660). Gitignored, unlike `hlds-dm01.vars.yaml` — it carries a real join password and this project has no vault yet. Needed two real generalizations to `steam_gameserver_instance` (proving out the "generic, data-driven" design against a second, differently-shaped game): `steam_gameserver_instance_extra_ports`/`steam_gameserver_instance_extra_protocols` (lists; Valheim needs 3 consecutive ports, and sources disagree on whether it needs TCP as well as UDP so both are opened) and `steam_gameserver_instance_env` (a dict rendered as `Environment=` lines in the systemd unit; Valheim's binary needs `LD_LIBRARY_PATH`/`SteamAppId` set or it fails to initialize its Steamworks networking layer). All default empty, so HLDS's rendered unit/ufw rules are byte-for-byte unaffected — verified by rendering the systemd template for both instances directly.

### Fixed

- `gameservers/valheim-1.vars.yaml`: removed `-crossplay`, and bumped `steam_gameserver_verify`'s port-bound retry budget from 6×5s (30s) to 12×5s (60s). What was reported as "listening on 127.0.0.1" turned out, on live inspection (`ss -tulnp`, `journalctl`), to be something worse: both HLDS and Valheim were actually correctly bound to `0.0.0.0` — Valheim was simply never fully starting. `-crossplay` requires successful PlayFab (Xbox/PlayStation crossplay backend) registration before the server opens its main game port, and it sat in an infinite "PlayFab reconnect" loop instead (confirmed 48+ minutes of uptime, port 2456 never bound, despite the VM having normal outbound internet access). Steam-only servers don't depend on PlayFab at all; removing the flag let it initialize normally (`Opened Steam server` in the journal, port 2456 bound within seconds) — it just needed a few seconds more than the original 30s verify window allowed, hence the retry bump.

- **Per-instance vars files were never actually isolated to one instance per run — a real, serious bug, not just a naming nit.** They lived at `inventory/group_vars/steam_linux/gameservers/*.vars.yaml`, and Ansible's `group_vars/<group>/` auto-loading recurses into subdirectories — so *every* file under `gameservers/` was loaded for *every* host in the `steam_linux` group, on *every* run, regardless of which one (if any) was passed via `-e @<path>`. Confirmed live: `ansible-inventory --host <host>` showed `steam_gameserver_config_role: hlds_dm_config` with **zero** `-e` flags at all. This surfaced concretely deploying `valheim-1`: `create-steam_gameserver.yaml` ran `hlds_dm_config`'s tasks against the Valheim install (which has no `valve/` mod directory), because `hlds-dm01.vars.yaml`'s `steam_gameserver_config_role` was auto-loaded and nothing in `valheim-1.vars.yaml` overrode it. It only ever looked correct for HLDS alone because there was no second file yet to collide with. Fixed by moving instance definitions out of `group_vars` entirely, to a sibling `gameservers/` directory at the project root (`inventory/group_vars/steam_linux/gameservers/` → `gameservers/`) — outside any inventory auto-load path, so `-e @<path>` is now the *only* way an instance's vars apply. All in-repo references (`create-steam_gameserver.yaml`, `Deploy.sh`, `README.md`, `.gitignore`, `roles/steam_base_verify`, `roles/steam_gameserver_instance`) updated; re-verified with `ansible-inventory --host` that no instance's vars leak in with zero or the *other* instance's `-e` flag.

- `create-steam_gameserver.yaml`: the dynamic config-role step used a static `roles:` list entry (`role: "{{ steam_gameserver_config_role }}"`, gated by `when:`) — Ansible resolves a role name in that list at parse time, **before** evaluating `when:`, so this only ever worked by accident, because HLDS's instance file happened to always define the var. The very first game that legitimately has no config role (Valheim) failed immediately with `'steam_gameserver_config_role' is undefined`, on a real run, not just `--syntax-check`. Switched to `ansible.builtin.include_role` as a task — a dynamic include that defers both the templating and the `when:` check to actual execution, so omitting the var now works exactly as designed. Verified against all three cases: no `-e` at all, an instance with a config role (HLDS), and one without (Valheim).

- `ansible.cfg` (real, gitignored) now sets `collections_path = ../.ansible/collections` — `create-steam_gameserver.yaml`, run directly with no `Deploy.sh`-style wrapper, failed with `couldn't resolve module/action 'community.general.ufw'` when `ANSIBLE_COLLECTIONS_PATH` wasn't exported in the shell (activating the venv alone doesn't set it). The canonical `../Shared/Ansible/ansible.cfg.example` gained the same line — see `Shared/CHANGELOG.md` for the depth caveat (this value is wrong one level deeper, i.e. for `Shared/Ansible/`'s own copy).

- `steamcmd_install`: the "Extract steamcmd" task failed on a real deploy with `dest '/opt/app/steamcmd' must be an existing dir` — `ansible.builtin.unarchive` requires `dest` to already exist as a directory, and nothing had ever created `steamcmd_install_dir` itself (`steam_prereqs` only creates its parent, `/opt/app`). Added a task creating it first. While in there, also fixed the extract task's ownership: it set `owner: root, group: root`, but the very next task (self-update) runs `steamcmd.sh` as `become_user: steam`, and SteamCMD writes its own updated files into that same directory — a root-owned, group-inaccessible install dir would have failed that write. Both the new directory-creation task and the extract task now use `steam_system_user` for ownership.
- `inventory/group_vars/proxmox_pve1/` removed from this project entirely. `proxmox_node`/`storage_pool`/`vm_template_name`/`vm_template_vmid`/`backup_storage_target` now come from the new shared `../Shared/Ansible/group_vars/proxmox_pve1/vars.yaml` (see `Shared/CHANGELOG.md`) instead of a per-project copy — recreating that file for every new project in this mono-repo was pure tedium, and these really are one value per cluster. `network_bridge`/`network_vlan_tag` moved into `inventory/group_vars/steam_linux/vars.yaml.example` instead (project-local, not shared) — a game-server host's bridge/subnet needs can legitimately differ from other projects, and this project alone may end up running several Steam-Linux VMs across different subnets for different stakeholders. `create-steam_linux.yaml`, `create-steam_linux_backup.yaml`, `Install-Prerequisites.sh`, `.gitignore`, `README.md`, and `roles/proxmox_preflight`'s failure messages all updated accordingly.
- `create_steam_vm` / `create-steam_linux.yaml`: fixed a real race hit on a live deploy — `useradd: user 'steam' already exists` failing `steam_prereqs`, despite `ansible.builtin.user` normally being idempotent. Root cause: `add_host` put the freshly-created VM into the `steam_linux` group under an IP-named `inventory_hostname`, but on any run *after* the first, `hosts.ini` already lists the same physical VM under `[steam_linux]` by its persisted hostname (written by a prior run's own persistence step, run earlier in the same play sequence). Play 3 (`hosts: steam_linux`) therefore targeted two different inventory names for one machine and ran them in parallel — two concurrent `useradd steam` calls, one winning and one failing. `add_host` now targets a distinct, run-scoped group (`steam_vm_new`) that never appears in the static inventory, and `create-steam_linux.yaml`'s configuration play targets that instead; the static `steam_linux` group remains solely for `create-steam_gameserver.yaml`'s later, separate runs.
