# Changelog

All notable changes to `Shared/` are documented here. Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Changed

- `Ansible/docs/ANSIBLE_VAULT_GUIDE.md` §13: two troubleshooting rows added, both found live — a vault/ansible command prompting interactively for the password (or "no vault secrets found") when run from a directory with no `ansible.cfg`, such as the repo root; and `ansible-vault requires the cryptography library`, which means the system/`~/.local` Ansible is running instead of this repo's venv.
- `Ansible/create-pve_svc_user.yaml`: the `ansible-vault encrypt` step now accepts `-e vault_encrypt_id=<label>`, appended as `--encrypt-vault-id <label>`. Needed when `ansible.cfg`'s `vault_identity_list` holds more than one identity (a bare `ansible-vault encrypt` can't pick one); unset = unchanged single-identity behaviour. Header comment updated.
- `Ansible/README.md`: the `ansible.cfg.example` bullet notes the multi-identity option (per-vault / per-site isolation) and points at `ANSIBLE_VAULT_GUIDE.md` §12.
- `Ansible/ansible.cfg.example` is now the **single canonical Ansible config example for the whole repo**, restructured into a `# ===== COMMON =====` block every project uses verbatim (including the one shared `vault_identity_list` — one vault password decrypts every project's `vault.yaml`) plus a `# ===== <project> =====` section per project for settings only that project needs. Every project (`Shared/Ansible`, `Proxmox-Forgejo`, `Proxmox-NextCloud`) copies it to its own gitignored `ansible.cfg`; `Proxmox-Forgejo/ansible.cfg.example` was deleted. Dropped the `callback_whitelist = timer, profile_tasks` line (not bundled in ansible-core 2.21; `ansible.posix` not installed — it only produced a load warning). `Ansible/README.md` documents the convention (new project ⇒ add its section here).
- `Ansible/build-all-templates.sh` renamed to **`Ansible/create-templates_from_manifest.sh`** (all in-repo references updated).
- `Ansible/create-template-linux.yaml`: the cloud-init drive is attached on **virtio-scsi (`scsi2`), not `ide2`**. Proxmox's `ide2` default is a CD-ROM on the emulated PIIX IDE controller, which enumerates slowly — sometimes after cloud-init's `ds-identify` early datasource scan has already run. On Arch (whose cloud-init generator runs `ds-identify` very early with `notfound=disabled`) the `cidata` label isn't visible yet, so cloud-init **disables itself for the whole boot** — no network config, build VM unreachable, "Wait for SSH" hangs. Intermittent (won or lost the race per boot). On virtio-scsi the seed disk enumerates with `scsi0`/`scsi1`, well before that check; NoCloud finds `cidata` on any bus. Existing templates (still `ide2`) are unaffected — the race is Arch-specific.
- `Ansible/create-template-linux.yaml`: the `/opt` mkfs-tools install is now OS-agnostic (`ansible.builtin.package`, `xfsprogs`/`e2fsprogs` by chosen fstype) and unconditional — was `ansible.builtin.apt` gated to Debian/Ubuntu on the assumption "EL/Arch already have xfsprogs". EL does; the minimal Arch cloud image does not, so `T-Arch` failed at `mkfs.xfs`. Added a pacman DB sync (`-Sy`, **not** `-Syu`) in the harden play before Arch installs: a full upgrade bumps the `linux` package and orphans the running kernel's modules, after which `mount /opt` fails with "unknown filesystem type 'xfs'"; the packages installed here have no kernel dependency so a plain `-Sy` + `-S` is safe.
- `Ansible/create-template-linux.yaml`: the harden play now starts with `wait_for_connection` (retried real SSH) instead of relying on Play 2's `wait_for` port probe. Debian 13 / Ubuntu 24.04+ socket-activate sshd, so systemd accepts the TCP connection (port "open") before the per-connection `sshd@` can serve it — it can't until cloud-init has generated the host keys — so the first real SSH attempt got `Connection refused`. `wait_for` on a socket-activated port can't see that gap; `wait_for_connection` retries through it.
- `Ansible/create-template-linux.yaml`: the cluster-wide "a `T-*` VM that isn't a template" guard no longer hard-fails on a **concurrent build of another manifest row**. It now splits the non-template `T-*` VMs by vmid: one that isn't in `template_manifest.yaml` at all is still a hard stop (genuine stray / name clash); one that IS a manifest row but not this run's target is treated as an in-flight sibling build (parallel `create-templates_from_manifest.sh` / an orchestrator) and only noted — a genuinely crashed build of that row is still caught precisely, when that row is next built, by the existing VMID-occupant check. This run's own target vmid is unaffected (still guarded by the occupant check). Without this, parallel builds were impossible: run #2's Play 1 always aborted on run #1's in-flight build VM.
- `Ansible/create-template-linux.yaml`: Play 1 now **pre-flights the CPU model against the build node**. It maps the resolved `template_cpu_type` to the host CPU flags that microarch level needs (v2 → `sse4_2`/`popcnt`/…, v3 → `avx2`/`bmi2`/`fma`/…, v4 → `avx512*`, `-AES` → `aes`), reads the node's `/proc/cpuinfo`, and fails fast naming the missing flags. Without it, an unsatisfiable `--cpu` (e.g. `x86-64-v3` for Rocky 10 on an Ivy Bridge node) surfaced only as an opaque "Reached timeout while waiting for starting VM" minutes later.
- `Ansible/create-templates_from_manifest.sh` + `template_configuration.yaml`: new optional `template_skip` list — names the wrapper skips (`skipped (template_skip)`, not counted as failures) for rows that can't be built in this environment for host reasons. Distinct from a manifest `stub: true` (build path not implemented anywhere); `template_skip` is per-site config, not committed. `T-Rocky-10-Cloud` is in it for this cluster (hydra has no AVX2). A direct `-e template_target=` run still executes and hits the CPU pre-flight.
- `Ansible/create-template-linux.yaml`: dropped `set-name: eth0` from the netplan-v2 build snippet. Ubuntu's cloud image uses predictable NIC names (`ens18`), so `set-name` made cloud-init try to rename an already-UP interface — it fails `[busy]`, cloud-init then reports the device "not present" and **skips the address/routes entirely**, so the build VM never got its IP (900 s SSH timeout, seen on Ubuntu 26.04). The `match:` on MAC already targets the right NIC without a rename, and the playbook connects by IP. Rocky was unaffected because its image sets `net.ifnames=0` (NIC is already `eth0`). Snippet is now: `match` + `dhcp4/6: false` + `accept-ra: false` + `addresses` + `routes` + `nameservers`, nothing else.
- `Ansible/create-template-linux.yaml`: the build VM's IP is now **derived from its VMID**, not configured. Config drops `template_build_ip` for `template_build_subnet` (a dedicated, pipeline-only `/24`); the playbook computes `<subnet prefix>.<(vmid - 90000) % 220 + 20>/24` in Play 1, asserts the `/24` and `vmid >= 90000`, caches it, and prints it. Because template VMIDs are globally unique this makes concurrent builds (5-10+ at once, the target for an automated pipeline) collision-free with no DHCP, IPAM or lock — a collision needs two VMIDs exactly 220 apart. Swap-in point for NetBox allocation later; nothing downstream changes. `template_build_gateway` / `template_build_nameservers` are unchanged. README gains a "build network" paragraph.
- `Ansible/create-template-linux.yaml`: `qm create` now passes **`--cpu`** (new `os_catalog.<os>.cpu_type`, default `x86-64-v2-AES`; Rocky/RHEL 10 → `x86-64-v3`; override per run with `template_cpu_type` in `template_configuration.yaml`). Proxmox's default `kvm64` is an x86-64-v1 baseline on which **RHEL/Rocky/Alma/Oracle 9+ kernels panic on boot** — the real reason the EL builds hung at "Wait for SSH" (verified live: Rocky 9.8 boots with `x86-64-v2-AES`, panics without). Debian/Ubuntu/Arch are unaffected by v1 but get the same modern, migration-safe floor. Documented limit: a pre-Haswell build host (no AVX2) cannot build the EL10 templates — noted on the `T-Rocky-10-Cloud` manifest row and in the config.
- `Ansible/create-template-linux.yaml`: the netplan-v2 network snippet's default route is now `to: 0.0.0.0/0`, not the netplan shorthand `to: default`. EL9 cloud-init hands the v2 config to its `sysconfig` renderer, whose v2→v1 route conversion throws `Address default is not a valid ip address` on the shorthand and then applies **no** network config at all (guest silently DHCPs — the second reason Rocky failed "Wait for SSH", after the CPU panic). `0.0.0.0/0` is accepted by every renderer, netplan included. Verified live: Rocky 9.8 takes `10.0.1.240` from the snippet with the CIDR form.

- **`setup_proxmox_automation_account.yaml` merged into `create-pve_svc_user.yaml` and removed.** One playbook now provisions the entire shared `svc_ansible` identity: the `svc_ansible@pve` PVE role/user/API token (written Vault-encrypted to `group_vars/proxmox_cluster/`) *and* the per-node Linux `svc_ansible` SSH account + scoped sudo + image cache dir. The API token is left alone on re-run unless `-e rotate_api_token=true` is passed (replacing the old interactive rotate-or-abort prompt, which also aborted the SSH-side setup). All three previously-fixed bugs in the bootstrap logic carry over verbatim.
- The shared automation account is named **`svc_ansible@pve`** everywhere (was documented as `ansible-automation@pve`; the deployed credential and node SSH account were already `svc_ansible`). Default `proxmox_api_username`, `proxmox_permissions.yaml`, `group_vars/proxmox_cluster/*.example`, and both project READMEs updated.

- `Ansible/create-template-linux.yaml` (renamed from `Create-Template.yaml`): now resolves what to build from a new committed `Ansible/template_manifest.yaml` — the single source of truth for the `name → VMID → OS/version` mapping of every template. `template_configuration.yaml` drops `template_os`/`template_os_version`/`template_name`/`template_vmid` in favour of one `template_target` naming a manifest row. Templates are allocated VMIDs from **90000** up (well clear of the 100-up range Proxmox's next-free-ID picker hands out to real guests); allocations are permanent and never renumbered.
- `Ansible/create-template-linux.yaml`: **no longer destroys anything.** The previous `qm stop`/`qm destroy --purge` of a stale VM at the target VMID is gone. Play 1 now fails fast instead when the target VMID is occupied by a non-matching guest, when a matching template already exists (a direct run — `create-templates_from_manifest.sh` turns this into a skip), or when *any* VM named `T-*` on the cluster is not a template (catches half-built templates from a crashed run). The operator resolves these by hand.
- `Ansible/inventory/hosts.ini`: added a `[proxmox_nodes]` entry mapping the Proxmox node's API name to its address and the minimal-privilege `svc_ansible` SSH account (passwordless sudo scoped to `qm`/`pvesm`, provisioned by `create-pve_svc_user.yaml`). The playbook's node steps call `sudo -n qm …` explicitly rather than escalating the module interpreter via `become`. `hosts.ini` holds real node names/IPs so it's gitignored (in `Shared/Ansible/.gitignore` and, as a bare `hosts.ini` pattern, in the repo-root `.gitignore`); only `inventory/hosts.ini.example` with placeholder values is committed.
- `Ansible/create-template-linux.yaml`: `qm importdisk` → `qm disk import` (the former is deprecated in PVE 8), the unused `cloud_image_download_dir` var removed, and `template_build_memory`/`template_build_cores` moved into the play that actually uses them (they were defined in a different play and were always undefined at point of use).
- `Ansible/create-template-linux.yaml`: the build VM now boots with a **static IP** (`template_build_ip` / `template_build_gateway`, new required config) instead of DHCP + a QEMU-guest-agent lease lookup — cloud images don't run the agent, so that lookup could never succeed (it hard-crashed the run). The harden play now waits for `cloud-init status --wait`, refreshes the apt cache, and installs + enables `qemu-guest-agent` in the template itself so *clones* report their IP and shut down cleanly.
- `Ansible/create-template-linux.yaml`: Play 1's fact cache now also carries `sysadmin_ssh_public_key`, `sysadmin_initial_password`, `template_target_node`, `template_mask_ssh_generator`, and the three `proxmox_api_*` values — Play 3 (harden) has no `vars_files` of its own and read them from `hostvars['localhost']`, where they didn't exist. Also fixed a non-boolean `assert` conditional (`| regex_search` → `is match`) that ansible-core ≥2.19 rejects.
- `Ansible/create-template-linux.yaml`: the imported cloud image's root disk is grown before first boot so cloud-init's growpart expands the filesystem. Cloud images ship a ~2 GB root — enough for Debian 12's build but not Ubuntu's `apt update` (fills the disk → `No space left on device`).
- `Ansible/create-template-linux.yaml` — **two-disk layout.** Root (`scsi0`) is now sized to an **absolute** `template_root_size` (default `16G`), parsed from `qm config` and **only grown to** — never shrunk (Rocky's 10G xfs can't shrink; an absolute `qm disk resize` down errors). Replaces the relative `template_disk_grow`. Every template also gets a **second disk** (`scsi1`, `template_opt_size_gb` GiB default 16, `serial=opt`) with a whole-disk filesystem (`template_opt_fstype`, default **xfs** — installs `xfsprogs` on Debian/Ubuntu) mounted at `/opt`, holding `/opt/app` (applications) and `/opt/data` (data + logs). fstab entry is `UUID=` with `defaults,nodev,nosuid,nofail,x-systemd.growfs` — **not `noexec`**. `scsi1` is not in the boot order; it's carried into the template and inherited by `full: true` clones, and `x-systemd.growfs` expands `/opt` on a clone that resizes `scsi1`. EL builds get `restorecon -RF /opt`. fstab is written with `ansible.builtin.blockinfile` — no new collection dependency.
- `Ansible/create-template-linux.yaml`: the `Restart sshd` handler is now OS-aware — `ssh` on Debian/Ubuntu (no `sshd` alias since Ubuntu 24.04 / Debian 13 moved to `ssh.socket`), `sshd` on EL/Arch.
- `Ansible/create-template-linux.yaml`: **first boot no longer runs a package upgrade.** A `--cicustom user=` snippet now replaces Proxmox's auto-generated cloud-init user-data — it creates the `sysadmin` bootstrap account (key-only) and sets `package_upgrade: false`. Proxmox otherwise injects `package_upgrade: true`, a full `apt`/`dnf` upgrade (~170s on a fresh image, minutes more with a kernel bump + dracut initramfs regen on Ubuntu 26.04) that repeatedly pushed first boot past the SSH wait. The harden play does a targeted `apt update` + guest-agent install instead. Replaces the `community.proxmox.proxmox_kvm` task that set `ciuser`/`sshkeys` via the API. The "Wait for SSH" ceiling is 600s → **900s** (a safety margin for a slow image pull / dracut run; normal first boot is now under a minute).
- `Ansible/create-template-linux.yaml`: the build VM's static IP is now delivered as a **netplan-v2 cloud-init network-config snippet** — written to `template_snippet_storage` (new config; a dir-type storage) and referenced via `qm set --cicustom network=`, matching on the VM's NIC MAC — instead of Proxmox's `ipconfig0`. `ipconfig0` emits cloud-init `network-config version: 1`, which Debian 12/13 and Ubuntu 24.04 honour but Ubuntu 26.04, Rocky 9/10 and Arch silently ignore (they DHCP, and the harden play can't reach them). Both snippets (`user-<vmid>.yaml` + `net-<vmid>.yaml`) and the `cicustom` reference are stripped and `ipconfig0` reset to `ip=dhcp` before templatizing so clones don't inherit them. New config: `template_snippet_storage`, `template_build_nameservers` (list — DNS for the build VM). `create-pve_svc_user.yaml` enables `snippets` content on that storage and makes its `snippets/` dir svc_ansible-owned. `T-Ubuntu-26.04-Cloud` / `T-Rocky-9/10-Cloud` / `T-Arch-*-Cloud` un-stubbed.
- `Ansible/`: **Arch templates are versioned.** The `T-Arch` row is now `T-Arch-<YYYYMMDD.serial>` (Arch's dated cloud-image version, e.g. `T-Arch-20260901.583572`) with `version` matching; `os_catalog.arch` fetches `images/v<version>/Arch-Linux-x86_64-cloudimg-<version>.qcow2` instead of the moving `latest/`. Bumping Arch = editing the row's `name` + `version` in place.
- `Ansible/`: **template names carry a `-Source` segment.** Shape is now `T-<Os>-<Version>-<Source>[-<Variant>]`; every manifest row has a required `source: Cloud | ISO` field and the name ends in `-Cloud` / `-ISO`. All current rows became `…-Cloud`; `create-template-linux.yaml` binds `template_source`, validates it, and fails fast on a `source: ISO` row (those will be built by a separate Packer project) or a missing/invalid source. `<Variant>` (a customisation-layer key) is documented and reserved but not yet wired. `template_configuration.yaml{,.example}` default target is `T-Debian-13-Cloud`; `Proxmox-Forgejo`'s `vm_template_name` is `T-Debian-13-Cloud`.
- `Ansible/template_manifest.yaml`: renumbered **contiguously** — `T-Ubuntu-22.04` removed and the rows below it shifted down (pre-1.0.0 the table may be renumbered freely; the retire-the-vmid discipline starts at 1.0.0). New optional `stub: true` field.

### Added

- `Ansible/docs/ANSIBLE_VAULT_GUIDE.md` — the complete Ansible Vault walkthrough, **relocated here from `Proxmox-Forgejo/docs/`**: it's generic Vault instruction every Ansible project uses, not Forgejo-specific, so it belongs with the shared toolchain (new `Ansible/docs/` dir mirrors `Proxmox-Forgejo/docs/`). Its running example is now the co-located `group_vars/proxmox_cluster/vault.yaml` (`deploy_forgejo.yaml` → `create-pve_svc_user.yaml` throughout), the Forgejo-specific base64 note is generalised to "watch for app-specific format constraints — the authoritative note is in each project's `vault.yaml.example`", and §12 is broadened from "second site" to multiple vault identities generally (one password per `vault.yaml` for blast-radius isolation, `create-pve_svc_user.yaml -e vault_encrypt_id=<label>`, and password-file placement — durable, outside `~/.ansible/`, back each up, may be an executable client script). Every in-repo reference (`README.md`, `create-pve_svc_user.yaml`, `create-template-linux.yaml`, `ansible.cfg.example`, `group_vars/proxmox_cluster/vault.yaml.example`, `template_configuration_vault.yaml.example`, `RUNBOOK-Regenerate_Vaults.md`, plus the `Proxmox-Forgejo/` files and `CLAUDE.md`) repointed.
- `Ansible/bootstrap.sh` + `Ansible/requirements.txt` + `Ansible/requirements.yaml` — build the repo-local Ansible toolchain: a Python venv at `<repo-root>/.venv` (`ansible-core` pinned, `cryptography` for Vault, `proxmoxer`, `passlib`) and Galaxy collections at `<repo-root>/.ansible/collections` (from this dir's `requirements.yaml` plus every `<repo-root>/*/requirements.yaml`). Both gitignored. Isolates the toolchain from the system Python — installing `cryptography` there was breaking other distro apps. Idempotent; re-run after editing a requirements file. `create-templates_from_manifest.sh` and the project `Deploy.sh` / `Install-Prerequisites.sh` wrappers put `.venv/bin` on `PATH` and export `ANSIBLE_COLLECTIONS_PATH` automatically; `README.md` documents `bootstrap.sh` and the activate-for-interactive path.
- `Ansible/README.md`: spelled out the clone-network contract — a `full: true` clone inherits the template's NIC on the build VLAN (`template_network_bridge`), so every consuming project must re-point `net0` at its own bridge and require an explicit bridge value in its preflight. (Prompted by `Proxmox-Forgejo` VMs silently coming up on the build VLAN.)
- `Ansible/update-vm_disk-grow.yaml` — online, no-downtime grow of one disk on a Proxmox VM. Given `-e VMID=<vmid> -e blockdev=/dev/sdX -e size=<+5G|40G> -e grow_ssh_user=<user> -e grow_ssh_key=<path>`, it resolves the VM's node and its Nth disk key from `qm config`, `qm disk resize`s it (via the shared `svc_ansible` SSH account), verifies the guest device actually grew (a wrong `/dev/sdX` mapping aborts before anything is touched), then auto-detects the in-guest topology — whole-disk filesystem / single partition / partition→LVM PV→root LV — and runs `growpart` + `pvresize`/`lvextend` + `xfs_growfs`/`resize2fs` as needed. Serves both the cloud-template layout (whole-disk xfs `/opt`, GPT single-partition root) and the planned ISO/Packer layout (GPT + LVM root). `README.md` "Disk layout" gains an "Automated grow" subsection.
- `README.md` — overview of the `Shared/` tree: the by-language layout (`Ansible/` in use; `Python/`, `Go/`, `BASH/`, `C/`, `CPP/`, `dotNET/` as scaffolds), how projects consume shared code, the one-way projects→Shared dependency rule, and the tree-wide conventions (single `CHANGELOG.md`, `.example`-file/public-repo hygiene, gitignored real vault files).
- `Ansible/template_manifest.yaml` / `create-template-linux.yaml` / `create-templates_from_manifest.sh` — `T-RHEL-9` / `T-RHEL-10` stub rows (`stub: true`) + an `os_catalog.rhel` placeholder. Play 1 fails fast on a stub row; `create-templates_from_manifest.sh` skips it (prints `skipped (stub)`). RHEL's KVM image needs authenticated Red Hat access — the rows reserve the name/vmid/design until that's wired up.

- `Ansible/create-pve_svc_user.yaml` — one-time, idempotent playbook that provisions the **whole** shared `svc_ansible` identity (see the Changed entry above). API half: the `svc_ansible@pve` role/user/token + the Vault-encrypted `group_vars/proxmox_cluster/` credential (folded in from the former `setup_proxmox_automation_account.yaml`). SSH half, on every host in `[proxmox_nodes]`: key-only `svc_ansible` login (password locked), `authorized_keys` set whole-file to the same `sysadmin_ssh_public_key` string from `template_configuration.yaml`, `/etc/sudoers.d/svc_ansible` granting NOPASSWD sudo for `/usr/sbin/qm` and `/usr/sbin/pvesm` only (visudo-validated), and the cloud-image cache directory owned by the account. Connects as a privileged admin whose SSH and sudo credentials are collected via `vars_prompt` — never on the command line or from a file. Replaces the previously undocumented by-hand setup.
- `Ansible/create-templates_from_manifest.sh` — walks `template_manifest.yaml` and runs `create-template-linux.yaml` once per row (`-e template_target=… -e batch_mode=true`), building the templates that are missing and skipping the ones that already exist. The "make all the base templates" entry point.
- `Ansible/create-template-linux.yaml`: persistent on-node cloud-image cache (`template_image_cache_dir`, default `/var/cache/vm-template-images`, created by `create-pve_svc_user.yaml`). Each cached image sits next to a `.checksum` sidecar (`<algo>:<hex>`); the playbook validates the cached image against it before any download, so a template rebuild after a valid cache hit needs **zero internet traffic**. A cached image that fails validation is deleted and re-pulled with a fresh upstream checksum; `-e refresh_image_cache=true` forces the re-pull. Replaces the previous per-run download into the SSH account's home that was deleted after import.

- `Ansible/` — shared, cluster-wide Proxmox automation account tooling (`create-pve_svc_user.yaml`, `proxmox_permissions.yaml`, `group_vars/proxmox_cluster/`) usable by any Proxmox-facing project in this mono-repo, so each project no longer needs its own copy of the credential-bootstrap flow. `ansible.cfg` is gitignored with a committed `.example` (public repo — the vault-id label/filename is personalizable).
- `Ansible/`: the real Ansible Vault files (`group_vars/proxmox_cluster/vault.yaml`, `template_configuration_vault.yaml`) are gitignored, not committed. Ciphertext is safe, but the `$ANSIBLE_VAULT;1.2;AES256;<vault-id>` header is cleartext and the `<vault-id>` names a credential on a real network. Only the plaintext `*.example` companions are committed; the real files are generated locally by `create-pve_svc_user.yaml` / `ansible-vault create`.
- `inventory/group_vars/all/vars.yaml` — pins `ansible_python_interpreter` to `/usr/bin/python3` (matching `Proxmox-Forgejo`) so `Gathering Facts` on `localhost` doesn't fail against a broken/unselected `pyenv` shim on systems where `pyenv` is installed alongside the system Python.
- `create-pve_svc_user.yaml`: fixed the "Abort if rotation was not confirmed" guard incorrectly firing on every first-time bootstrap (no existing credential) — it checked `confirm_rotate is defined`, but a skipped task with `register:` still registers a stub result, so that check was always true. Now re-checks the same real conditions as the preceding pause task instead.
- `create-pve_svc_user.yaml`: fixed `proxmox_ssh_host` (a `vars_prompt` variable) and `vault_file_path`/`vars_file_path` (Play 1's own `vars:` block) never being cached into facts, so Play 3 failed trying to read them back — none of a play's `vars:`/`vars_prompt` values are visible in a later play without explicit caching. All three are now cached alongside the other bootstrap variables, in one place, so Play 1's `vars:` block stays the single source of truth for the file paths.
- `create-pve_svc_user.yaml`: `group_vars/proxmox_cluster/vars.yaml` never bridged the vaulted `vault_proxmox_api_token_secret` to the plain `proxmox_api_token_secret` name every consuming project's `module_defaults` actually references — the vars.yaml/vault.yaml double-variable pattern used everywhere else in this mono-repo was missing its second half here. Fixed in the generator (future bootstraps) and patched the already-generated file directly (no need to re-run the whole bootstrap, which would have also triggered an unnecessary token-rotation prompt). Verified by resolving the real value at runtime, not just a syntax check — an earlier check of this same fix gave a false negative from a test file placed in the wrong directory (relative `vars_files:` paths resolve against the *playbook's* directory, not the shell's cwd).
- `Create-Template.yaml` — builds a hardened, cloud-init-ready Proxmox VM template (Debian, Ubuntu, Rocky Linux, or Arch Linux), moved here from `Proxmox-Forgejo` since template-building isn't specific to any one project. Bakes in a random unspoken root password with SSH forbidden entirely, and a `sysadmin` account (NOPASSWD sudo, key-only SSH) on every build regardless of OS. Configuration lives in `template_configuration.yaml`/`template_configuration_vault.yaml` (real files gitignored, `.example` companions committed) rather than under `group_vars/` — it's input to a single admin script, not a property of any inventory host/group. Verified live against real image sources: checksum-fetch-and-parse for all four OSes (including Rocky's BSD-style `SHA256 (file) = hash` format, which needs different extraction logic than the other three) confirmed against their real, current manifests. A full `T-Debian-12` build has since run end-to-end against a live cluster (cache → import → static-IP boot → harden → templatize); the other targets are not yet built — see the playbook's own header comment.
